# Goal: 웹에서 클러스터를 등록하고 관측하는 chDB Mini LogHouse PoC

## 1. 목표

사용자가 웹에서 ClickHouse 클러스터의 endpoint·계정·password를 등록하고, 해당 클러스터의 수집 상태와 실제 데이터 기반 Dashboard를 확인할 수 있는 PoC를 구현하라.

핵심 사용자 흐름은 다음과 같다.

> 클러스터 추가 → 연결·권한 검사 → 저장 및 수집 시작 → 클러스터 목록에서 상태 확인 → 상세 Dashboard 조회

수집·분석의 원안은 **앱 내 chDB + Refreshable Materialized View(RMV) + remote()/remoteSecure()**다. SysEx, OTel Collector, Kafka 같은 별도 수집 서비스를 도입하지 않는다. 웹 인터페이스는 선택 사항이 아니라 필수 산출물이다.

단순 UI mockup이 아니라 실제 ClickHouse에서 수집한 데이터가 화면에 표시되는 end-to-end PoC를 목표로 한다. 동시에 chDB RMV의 실제 실행·지속성·장애 복구 조건을 검증한다. 미검증 기능을 지원 또는 미지원으로 미리 단정하지 마라.

## 2. 사용자 요구와 설계 범위

### 사용자가 확정한 요구

1. 수집·모니터링할 ClickHouse 클러스터를 endpoint와 권한 있는 계정·password로 추가한다.
2. 추가한 ClickHouse의 상태 및 Dashboard를 웹에서 확인한다.

### 이번 PoC의 기본 가정

- 단일 운영자가 로컬 또는 신뢰할 수 있는 개발 환경에서 사용하는 앱이다.
- 기본적으로 loopback에만 bind하며 공개 인터넷 배포를 하지 않는다.
- 기존 프로젝트의 기술 스택을 우선한다. 새 프로젝트라면 유지보수가 단순한 Python backend와 최소한의 웹 UI를 선택하고 이유를 짧게 기록한다.
- source endpoint·등록 정보와 수집 telemetry를 구분한다. telemetry는 chDB에 저장하고 등록 metadata 저장 방식은 최소 구성으로 선택한다.
- 저장된 데이터 조회는 chDB를 사용한다. Dashboard를 열 때마다 모든 원격 클러스터를 직접 다시 조회하는 방식으로 대체하지 않는다.
- 사용자 브라우저가 닫혀도 backend가 살아 있으면 수집은 계속되어야 한다.
- 클러스터 수정·삭제·일시정지, 복잡한 알림, 사용자 관리 등은 필수 흐름 완성 후에만 검토한다.

## 3. 안전 경계와 사전 점검

- 적용되는 AGENTS.md와 프로젝트 규칙을 읽고 기존 작업을 보존한다.
- PoC 전용 디렉터리에서 작업하며 기존 파일·캐시·Docker volume을 임의로 삭제하지 않는다.
- 설치 전에 OS/CPU architecture, Python, Docker 사용 가능 여부, 메모리와 가용 디스크를 확인한다.
- 이전 조사에서는 디스크 부족과 macOS 바이너리 import 오류가 있었다. 현재 상태를 재확인하고 환경 오류를 SQL 기능 미지원으로 해석하지 마라.
- chDB 패키지·내장 ClickHouse engine·원격 ClickHouse 서버 버전을 기록하고 dependency를 고정한다.
- 기술적 불확실성은 공식 문서·소스 코드·실행 결과로 확인한다.
- 유료 Cloud 리소스 생성, 운영 클러스터 설정 변경, 계정 권한 확대는 하지 않는다.
- 장애 주입·테스트 workload·서버 설정 변경은 PoC가 소유한 테스트 인스턴스에서만 수행한다.
- 외부 연결에는 TLS와 최소 권한을 사용한다. 평문 remote()는 격리된 로컬 테스트에서만 허용한다.
- 같은 실패를 반복하기보다 원인을 분류하고 가설을 갱신한다. 환경 제약이 지속되면 안전하게 가능한 작업을 마친 뒤 필요한 변경과 미검증 항목을 보고한다.

## 4. 필수 화면과 사용자 시나리오

### 화면 A — 클러스터 추가

필수 입력:

- 표시 이름
- endpoint(host와 port)
- TLS 사용 여부
- username
- password(masked input)

입력 안내에는 수집 경로가 요구하는 프로토콜을 명시한다. remote/remoteSecure에 필요한 native endpoint와 HTTP endpoint를 혼동하지 않도록 검사·안내한다. port만 보고 서버 구성을 임의로 단정하거나 조용히 다른 endpoint로 바꾸지 마라.

사용자 동작:

1. 정보를 입력하고 `연결 테스트`를 누른다.
2. backend가 timeout 내에 실제 연결·인증 및 필수 system table 조회 권한을 확인한다.
3. 성공 여부, 서버 버전, 수집 가능한 데이터와 확인된 노드 범위를 표시한다.
4. `저장 및 수집 시작`을 누르면 등록 정보를 보존하고 backend 수집 작업을 구성한다.
5. 목록 또는 상세 화면으로 이동하여 `첫 수집 대기`에서 실제 수집 상태로 전환되는 과정을 볼 수 있다.

오류 UX:

- 잘못된 endpoint, timeout/연결 거절, TLS 오류, 인증 실패, 권한 부족을 가능한 범위에서 구분한다.
- 원인을 확인할 수 없는 경우 추측하지 않고 미분류 오류로 표시한다.
- 접속 성공과 system table 조회 가능 여부를 별도로 표시한다.
- 필수 수집 권한이 없으면 정상 등록·수집 완료로 표시하지 않고 수정 및 재시도를 안내한다.
- 필수 테이블이 비활성화되었거나 존재하지 않으면 권한 오류와 구분한다.
- 이중 클릭이나 요청 재전송으로 중복 등록·중복 수집 작업이 생성되지 않도록 한다.

### 화면 B — 클러스터 목록 / Overview

등록된 클러스터마다 다음을 표시한다.

- 이름과 endpoint
- 최근 연결 확인 결과와 확인 시각
- 수집 상태: 준비 중 / 첫 수집 대기 / 수집 중 / 수집 지연 / 수집 오류
- 마지막 성공 수집 시각과 경과 시간
- 확인된 노드 수 및 수집 범위: 전체 검증됨 / 일부 / 미확인
- 최근 오류의 안전한 요약
- 상세 Dashboard 이동

빈 상태에서는 `클러스터 추가`를 안내한다. loading, empty, error, stale 상태를 구분한다.

**연결 성공, 수집 성공, 관측한 클러스터 상태는 서로 다르다.** 접속이 된다는 이유만으로 클러스터 전체를 `정상`이라고 표시하지 마라. stale 판정 기준은 수집 주기 및 허용 지연과 연결하여 설정하고 표시한다.

### 화면 C — 클러스터 상세 Dashboard

공통 정보와 조작:

- 클러스터 이름, 연결 확인 결과, 수집 상태, 마지막 성공 시각
- 실제 관측 노드와 수집 범위
- 기간 필터: 최근 15분 / 1시간 / 24시간
- 노드 필터, 수동 새로고침, 자동 화면 갱신
- 표시 시간대 및 데이터 freshness

필수 데이터:

1. 수집 가능한 주요 metric의 현재값과 시계열 차트
2. 선택 기간의 쿼리 건수와 실패 건수
3. 쿼리 실행 시간 p95 및 시간대별 쿼리 건수 추이
4. 최근 쿼리·느린 쿼리·오류 쿼리를 확인할 수 있는 테이블

테이블에는 출처 노드, 이벤트 시각, query_id, 이벤트 종류, 실행 시간, 필요한 경우 SQL/오류 요약을 표시한다. SQL 원문은 접어서 표시하고 민감정보·접근 범위를 고려한다.

집계 원칙:

- QueryStart/QueryFinish를 같은 쿼리 두 건으로 세지 않는다.
- 논리 요청 수와 분산 쿼리의 노드별 실행 건수를 구분하고 집계 정의를 문서화한다.
- p95의 대상 이벤트, 실패 건수 정의, 중복 제거 기준을 명시한다.
- 데이터 없음, 미수집, 권한 부족, 실제 0을 구별한다.
- 수집 중단 시 과거 차트를 유지하되 stale임을 명확히 표시한다.
- 실제 수집하지 않은 CPU·디스크 등의 수치를 mock 또는 임의 추정으로 채우지 않는다.
- 사용자 입력, SQL 원문, 서버 오류 메시지는 HTML로 실행되지 않도록 안전하게 렌더링한다.

## 5. 자격증명과 backend 실행 모델

- 브라우저는 backend API만 호출한다. 원격 ClickHouse 접속은 backend/chDB에서 수행한다.
- password를 URL, localStorage, 일반 API 응답, 로그, 예외 메시지, 테스트 screenshot에 노출하지 않는다.
- password는 제출 후 폼에서 지우고 조회 API로 원문을 반환하지 않는다.
- 비밀번호를 재시작 후에도 보존한다면 암호화하고 키는 저장 데이터·저장소와 분리한다. 실제 비밀값을 Git에 넣지 않는다.
- 메모리만 보관하는 최소 구현을 선택하면 재시작 후 재입력이 필요함을 UI/README에 명시하고 자동 재연결을 구현했다고 주장하지 않는다.
- chDB MV DDL, named collection, engine metadata, debug log에 생길 수 있는 비밀정보 복사도 점검한다. 앱 등록 테이블만 암호화하고 전체 저장 경로가 안전하다고 주장하지 않는다.
- 사용자 입력을 SQL에 무검증 문자열 연결하지 않는다. 지원되는 parameter binding 또는 검증·안전한 quoting을 적용하고 identifier 생성도 통제한다.
- UI와 수집기의 수명을 분리한다. HTTP 요청, 페이지 재렌더, 브라우저 자동 갱신이 수집기를 재생성하지 않게 한다.
- 영속 chDB connection 및 수집 작업의 소유자를 명확히 한다. web worker나 개발용 reload로 수집기가 중복 실행되지 않도록 한다.
- timeout, 동시 수집 수, 쿼리 자원 사용을 제한한다. 노드 하나의 장애가 모든 수집과 UI 요청을 막지 않도록 한다.
- same-origin을 기본으로 하고 임의 origin에 credential 관련 API를 개방하지 않는다. 상태 변경 요청에는 선택한 웹 스택에 맞는 CSRF/origin 방어를 적용한다.
- 다중 사용자/외부 공개 인증·인가와 운영용 endpoint 접근 정책은 이번 PoC의 기본 범위 밖이다. 외부 공개 가능한 제품이라고 보고하지 마라.

## 6. 데이터 수집 및 topology

필수 source는 다음 두 종류로 제한한다.

- `system.metrics`: 관측 시각을 붙여 snapshot 이력을 APPEND한다.
- `system.query_log`: 수집 구간과 중복·지연 도착·재시작 복구를 관리한다.

추가 system table은 명확히 필요한 경우에만 범위를 설명하고 도입한다. `SELECT *`에 의존하지 말고 버전별 필요한 컬럼과 capability를 확인한다.

데이터에는 cluster_id, node_id, source_event_time(있는 경우), collected_at 등 출처와 시각을 남긴다. source node 식별이 수집 앱의 hostname으로 잘못 대체되지 않았는지 검증한다.

클러스터 endpoint 하나가 모든 노드의 system table을 제공한다고 가정하지 마라. 실제 topology에 맞는 전체 노드 조회 경로를 검증한다. 전체 범위를 확인하지 못하면 endpoint/일부 노드 범위로 명시하고 등록 자체와 전체 클러스터 검증을 구별한다.

실제 테스트 대상이 제공되지 않았다면 로컬 ClickHouse 인스턴스를 사용한다. 기본 topology는 A의 2개 노드 + B의 1개 노드이며 실제 업무 데이터 복제는 필수가 아니다. 자원 부족으로 A/B 각각 1개 노드로 축소하면 다중 노드 수집 검증을 NOT_RUN으로 남긴다.

## 7. 검증 순서

### Phase A — chDB RMV 최소 실증

웹 UI를 크게 만들기 전에 다음을 작은 실험으로 확인한다.

1. 영속 경로와 connection/session 생성
2. 로컬 테이블에 실행 시각을 기록하는 REFRESH ... APPEND MV 생성
3. 동일 connection을 유지하며 SQL을 보내지 않는 유휴 구간 확보
4. 유휴 중 서로 다른 시각의 refresh가 최소 3회 발생했는지 검증
5. 종료·재시작 후 데이터/MV 정의 보존 및 반복 실행 재개 확인

최초 생성 또는 재접속 직후의 refresh 한 번으로 반복 스케줄링을 입증하지 마라. 실패 시 버전·명령·오류·최소 재현 코드를 남기고 환경 실패와 SQL/scheduler 실패를 구별한다.

### Phase B — 등록에서 Dashboard까지 첫 실제 경로

1. 웹 추가 폼과 연결·권한 검사 API 구현
2. 등록 metadata 및 credential 처리 구현
3. 노드 하나에 대한 RMV 원격 수집 구성
4. chDB의 실제 수집 결과를 목록과 상세 Dashboard에 표시
5. 다른 클러스터 등록 및 데이터 분리 검증

중간 UI fixture는 개발에 사용할 수 있으나 실제 수집 데이터로 교체되지 않은 화면을 완성으로 보고하지 마라.

### Phase C — 정확성과 장애 복구

- 노드마다 식별 가능한 테스트 query_id를 발생시키고 source와 destination의 안정화된 이벤트 집합을 대조한다.
- overlap·재시도 후 raw 중복과 Dashboard 집계 중복을 각각 측정한다.
- query_id만으로 서로 다른 이벤트를 합치지 않도록 dedup 키를 검증한다.
- 비동기 flush에 대한 safety lag, overlap, backfill 정책을 구현하거나 해당 한계를 재현한다.
- 노드/테이블별 마지막 성공 수집 구간의 저장·복원 방식을 설명한다. max(event_time)만으로 완전한 수집을 가정하지 않는다.
- 수집 앱 중단 중 source에 테스트 이벤트를 발생시키고 재시작 후 복구 범위를 확인한다.
- PoC 노드 하나를 일시 중단했을 때 다른 노드 수집, 오류/stale 표시, 복구 후 동작을 확인한다.
- 브라우저 탭을 닫아도 수집이 지속되는지, 화면 갱신/여러 탭이 중복 수집을 만들지 않는지 확인한다.
- backend 재시작 후 등록 목록·이력이 유지되는지, credential 정책에 맞게 재연결 또는 재입력 상태로 복구되는지 확인한다.

RMV의 APPEND를 자동 source 증분 수집이나 exactly-once 보장으로 취급하지 마라. 사용할 버전의 APPEND INCREMENTAL이 remote source에 적용되는지 별도로 확인하고 이름만 보고 대체하지 마라.

### Phase D — 브라우저 E2E 확인

실제 브라우저 또는 자동화 도구로 다음을 검증하고 증거를 남긴다.

- 정상 등록 → 첫 수집 → 실제 차트/테이블 조회
- 잘못된 password → 안전한 오류 표시 → 수정 후 재시도
- 필수 system table 권한 부족 → 제한 원인 표시
- endpoint 연결 실패 → UI가 멈추지 않고 실패 표시
- 데이터가 아직 없는 상태와 실제 0의 구분
- 노드 장애 → 수집 오류/stale 표시, 다른 클러스터 정상 조회
- 기간/노드 필터의 실제 API·SQL 반영
- password가 API 응답·로그·화면에 노출되지 않음
- 주요 화면의 layout, loading/error 상태 및 browser console 오류 확인

## 8. 원안이 성립하지 않을 때

우선 검증 대상은 반드시 chDB RMV가 직접 remote를 실행하는 방식이다. 검증 전에 Python timer나 중앙 ClickHouse server로 조용히 대체하지 마라.

실제로 제약이 확인된 경우 다음을 비교한다.

- 앱 내부 timer + chDB INSERT INTO ... SELECT remote(...)
- 중앙 ClickHouse server + RMV + remote(...)

대안 구현은 확인된 제약을 해소하는 최소 실험으로 제한한다. 변경한 실행 경로와 담당 책임을 명시하고 대안의 성공을 원안의 성공으로 보고하지 마라.

상시 운영이 필요하다는 이유만으로 chDB를 탈락시키지 마라. 상주 backend와 브라우저 UI의 수명은 구분할 수 있다.

## 9. 산출물과 완료 판정

필수 산출물:

- 실행 가능한 웹 UI + backend + chDB 수집 경로
- 등록 metadata, 수집 schema, RMV SQL 및 migration/bootstrap 방법
- 비밀정보 없는 설정 예시와 고정된 dependency
- 로컬 테스트 source/workload 구성
- 단순하고 재현 가능한 실행·테스트·종료 명령
- 통합 테스트 및 브라우저 E2E 결과/주요 화면 screenshot
- README와 `reports/feasibility.md`

보고서는 결론 → 근거 → 리스크 → 대안 순서로 작성한다. 버전/환경, 가설별 PASS·FAIL·NOT_RUN, 실제 수집 범위, 누락·중복·지연, 자원 사용, 자격증명 저장 정책, 재시작·장애 동작, 남은 한계를 포함한다.

Web PoC 성공은 다음이 모두 확인된 경우에만 선언한다.

1. 사용자가 웹에서 두 개 이상의 테스트 클러스터를 등록할 수 있다.
2. 실제 연결과 필수 권한이 검사되고 안전한 오류 UX가 제공된다.
3. 선택한 수집 경로가 주기적으로 실제 데이터를 chDB에 저장한다.
4. 각 클러스터의 상태·freshness·수집 범위와 실제 Dashboard를 볼 수 있다.
5. 주요 장애·재시작·중복 검증 결과와 재현 방법이 남아 있다.
6. backend API뿐 아니라 브라우저 사용자 흐름도 실제 검증되었다.

원래 RMV 경로의 기술적 불가능이 재현되면 버전 한정 근거와 대안을 제시하되, 웹 앱이 미완성이면 그 상태도 그대로 남긴다. 기술타당성 판정과 앱 구현 완료를 구별한다. 환경/권한 때문에 실행하지 못한 항목은 INCONCLUSIVE/NOT_RUN이며 성공 또는 기능 미지원으로 바꾸지 않는다.

작업 시작 시 짧은 구현 계획과 환경 점검 결과를 제시한 뒤 안전하게 가능한 검증부터 진행하라. UI 구현만으로 완료하거나, 문서 조사만으로 실행 검증을 대신하지 마라.
